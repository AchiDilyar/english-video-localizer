## 主图准入条件

以下五条同时满足才可接入当前版本的主图，由 F 在“待接入 → 已接入”时逐项确认：

1. 不改变 `workflow.md` 第 5 节的基本版边界；
2. 不改变 `contracts/`，或契约变更已走 `CHANGELOG.md`；
3. 节点签名符合 `state: GraphState -> dict`，增量键在 `GraphState` 中已定义；
4. 有 mock 或固定样例可复现，不依赖真实模型密钥；
5. F 在本表把状态改为“已接入”。

## 状态定义

- **开发中**：提出者正在开发。
- **待接入**：提出者已完成，向 F 报告，等待 F 评估。
- **已接入**：确认会进入主图，或者在主图后续版本进入。
- **独立增量**：保留为独立工作，不进主图，但“进主图”栏可标“待定”，后续可重新评估。
- **待确认**：提出者登记的说明未能提供足够信息，F 需要等待开发者的进一步回应。
- **未登记**：提出者已提交代码但未在增量变更表中登记，由F代为登记。

## 详细说明文档规则

1. **需要详细说明时，在 `docs/design/increments/` 下新建一个 markdown 文件**，文件名使用增量的英文标识符（如 `webui.md`），并在登记表“详细文档”栏填相对路径。不需要详细说明的，此栏填“—”。
2. **每个增量最多一个详细说明文档。** 不要为同一个增量拆分成多个文件；如果内容过多，优先精简。
3. **详细文档只放必要信息**：增量是什么、影响哪些节点/产物、是否进主图、接入需要改什么。不要求写完整设计、不要逐行说明代码。
4. **历史文档可作为参考链接**，不需要迁移到 `increments/`。例如 B 的 `B-real-diarization.md` 可以继续放在 `docs/nodes/asr_diarize/`，登记表的“详细文档”栏指向它。

## 登记规则

1. **谁提出谁加一行。** 提出者只需填“增量、提出者、影响范围、详细文档”，状态默认为“开发中”，不要求写详细设计。
2. **接入主图由 F 决定。** F 在“待接入 → 已接入”时更新 `workflow.md`、`dataflow.md`、`contracts/`、`CHANGELOG.md`。
3. **不接主图的增量，F 不动四份文档**，只在表里标记。
4. **冲突时以 `docs/design/` 四份文档和 `contracts/` 为准。** 本表是索引，不是事实源。
5. **状态变更只由 F 或提出者改。** 提出者可以改“开发中 → 待接入”，F 改“待接入 → 已接入 / 独立增量 / 待定”。
6. **F主动发现的增量。** F 主动发现提交的代码中存在未登记的增量时，代填一行，状态标“未登记”，进主图为“待定”。提出者看到登记信息后可补充相关信息，并将状态从“未登记”修改为其他状态。

## 未登记或不回复的处理方案

本节适用于任何进行了基础版约定以外增量开发并已提交代码的角色：增量未在登记表登记，或已登记但未对 F 的确认请求作出回应。按影响程度分层处理。

后续说明中，“主图文件范围”包括：
- `docs/design`下的`workflow.md`、`dataflow.md`、`architecture.md`
- `project/graph`模块的所有文件
- `tests/graph`目录下的所有文件

### 进行增量开发，且增量文件只涉及自己的模块

典型情况：只改自己节点内部、自己的测试、自己的文档、独立工具脚本，所有文件都位于该角色负责的目录内。

处理：
- F 在登记表代填一行；
- 如果不阻塞主图，不主动介入。

### 增量文件不涉及主图文件范围

典型情况：新增目录、新增独立工具、新增节点文档，未改已有节点、契约、配置。

处理：
- F 在登记表代填一行；
- 如果不阻塞主图，不主动介入。
- 提出者应补充详细信息，由F评估是否接入主图后续版本
- 长时间未回复且 F 评估认为代码不具备接入主图条件的，不接入主图。

### 修改主图文件范围内已有的内容

典型情况：改 `workflow.md` 节点清单、改 `contracts/` 字段、改 `config/mock.toml` 键、改 `project/graph/` 或 `tests/graph/`。

处理：
- 登记表代填一行。
- 如果改动影响主图可运行性，F 接管；
- F 优先保证主图可运行性，且不影响原`workflow.md`中设计的节点，其他影响概不负责；
- 如果改动合理，F可能会部分采纳。但这不代表F允许修改主图范围的行为，请通过各种方式与F沟通说明想法，不得擅自改动主图文件范围内的文件。

### 节点或主图必要产物长期未交付

典型情况：负责某节点的角色长期未交付，或交付物接入主图后不可正常运行且不回应。

处理：
- F 评估自己实现最小版本的可行性；如果时间不允许，找其他角色协助；
- 主图先用最小实现跑通，提出者的版本作为参考，后续再评估是否替换；
- 登记表记录“未交付，F 最小实现”。

### 跨层通用规则

1. **主图不阻塞。** 任何一层的处理都不延迟 F 的主线动作。
2. **事实源保护。** 如果主图文件范围被改动，F 接管；其他区域不干预。
3. **汇报口径统一。** 未接入主图的增量，在 A/G 汇报材料中标注为“独立增量”或“未接入”，不混入主流程。
4. **后续回应仍可评估。** 如果提出者在截止后很久才回复，F 仍会按正常流程处理
5. **记录优先于判断。** 登记表只记录“谁、改了什么、是否登记、F 是否评估”，不对意图、态度作任何判断。
