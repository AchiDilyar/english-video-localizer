# 团队协作约定

版本：v1.3.0
最后更新：2026-11-09

---

## 1. 文档定位

本文档描述团队协作约定。项目设计以 `workflow.md`、`dataflow.md`、`architecture.md` 为准；团队分工以 `project-plan` 为准。本文档不替代上述文档。

---

## 2. 节点问题处理原则

1. 负责的节点出现问题时，由负责成员自行解决，不依赖其它节点或其它角色。
2. 跨节点问题（如接口不一致、产物定义冲突）按第 4 节协商流程处理。

---

## 3. 问题上报与汇报素材

1. 如果认为问题有价值，可与 A 和 G 交流，作为汇报素材。
2. A 和 G 决定是否纳入讲稿或 PPT。
3. 考虑项目要求，与“大模型和智能体”有关的、能够体现项目特点的问题最好

---

## 4. 职责与数据变更协商流程

1. 认为角色职责或相关数据需要变更时，必须与 F 协商。
2. F 评估修改对整个项目的影响。
3. 确定需要修改后，F 在 `docs/design/CHANGELOG.md` 中如实记录。
4. F 将改动告知所有受影响的角色。
5. 其它角色不可擅自修改 `docs/design/` 下的 `workflow.md`、`dataflow.md`、`architecture.md` 和 `collaboration.md`。

## 5. design目录下文档版本管理

### 5.1 版本管理

版本号变更规则：
- major（1.x -> 2.0）：不兼容的约定变更。如节点签名改变、事实源范围重划、产物名批量改名、文档集结构调整。
- minor（1.0 -> 1.1）：向后兼容的规则/章节增加。如新增产物、新增规则、新增章节。
- patch（1.0.0 -> 1.0.1）：措辞修正、笔误、格式调整、示例更新，不改变任何规则语义。

四份文档使用统一的版本号体系。文档有修改时，将该文档的版本号更新至最新。文档无修改时，可以保留原版本号，不要求任意时刻的四份文档版本号一致。

### 5.2 变更记录位置

四份文档（`workflow.md`、`dataflow.md`、`architecture.md`、`collaboration.md`）的变更统一记录在：

```text
docs/design/CHANGELOG.md
```

四份文档不单独维护变更记录。`CHANGELOG.md` 按 5.3 节的格式书写。

### 5.3 变更记录格式

每条记录包含以下内容：
- 标题：修改日期 + github 提交的标题
- 版本变更：格式为 `旧版本` -> `新版本`
- 涉及的文档
- 修改内容
- 修改原因

示例：

```markdown
## 2026-11-09 refactor(contracts): GraphState 改为 Pydantic 模型
### 版本变更
`v1.0` -> `v1.0.1`
### 涉及文档
- `dataflow.md`
- `architecture.md`
### 修改内容
- `GraphState` 从 `TypedDict` 改为 Pydantic `BaseModel`
### 修改原因
- 统一 `contracts/` 与 `utils/io.py` 的类型体系，使 `GraphState` 可被 Pydantic 校验、可被 `read_artifact`/`write_artifact` 直接处理，消除未来落盘/检查点时的嵌套模型退化风险。
```

## 6. 项目文档的职责

1. 项目文档不规定格式和内容。
2. 项目文档应完成的职责：
   - 便于节点负责人自己维护代码逻辑；
   - 便于 A 和 G 了解节点实现逻辑，用于汇报展示。
3. 项目文档的具体形式由各角色自行决定。
